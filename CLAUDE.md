# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A single userscript, `hilton-pro-tools.user.js` (Tampermonkey/Violentmonkey, `@match https://www.hilton.com/*`, `@run-at document-start`, `@grant none`). It adds a panel to hilton.com search results with three tools: an Aspire **resort credit finder** (Semi-Flex, deposit-required, refundable, non-Advance-Purchase rates at hotels on Hilton's official Resort Credit list), a **cash vs. points** comparison, a **free night finder** (where a Free Night Certificate, i.e. a Standard Room Reward, is available and worth the most), a **split stay** optimizer (cheapest mix of cash, points and certificate nights, optionally with one hotel change) **flexible dates** (the same stay with the arrival moved a few days, as a hotel × arrival day calendar), a **rate inspector** (every rate plan of one hotel and room type side by side), a **suite finder** (suites and upgrades per hotel with their markup in cash and points) and a **price watch** (watched stays re-priced on later visits, with a rebook badge when they get cheaper).

There is no build step, linter or bundler. The file is **plain JavaScript**: it is installed as-is and the preview harness injects it verbatim with `page.addInitScript`. `package.json` exists only for the preview harness (Playwright as a dev dependency, `pnpm test`).

## Files

- `hilton-pro-tools.user.js` — the whole script, one IIFE.
- `hilton-pro-tools.meta.js` — a copy of the userscript header only. `@updateURL` points here so update checks fetch just the header; `@downloadURL` points at `hilton-pro-tools.user.js`. Keep it identical to the header in `hilton-pro-tools.user.js` (especially `@version`).
- `README.md` — repo landing page: short overview, installing Tampermonkey and the script, development. Keep install links and the tool summary in sync with the header and `info.md`.
- `info.md` — user-facing description (published script page). Keep it in sync when behaviour, UI labels, settings or limits change.
- `changelog.md` — per-version changes, newest first, grouped as Added / Changed / Fixed. Bump `@version` in the userscript header together with a new changelog entry.
- `test/preview.js` — Playwright harness that runs the script against mocked hilton.com responses and screenshots the panel.

## Architecture

The script is organized into sections marked by `// ====` banner comments. The flow across them:

1. **Passive capture.** `window.fetch` and `XMLHttpRequest` are wrapped to *observe* (never modify) Hilton's own requests to `/graphql/customer`. Each request/response pair goes to `ingest()`, which picks up the destination search (hotel list, cash prices, search input/currency), hotel names from `hotelSummaryOptions`, etc. Own requests use `nativeFetch` (captured before wrapping) so they are not re-ingested.
2. **Search generations.** `state.generation` is bumped by `invalidate()` when `syncLocation()` / `locationKey()` detects a new destination or dates; async work carries the generation it started with and drops results if it changed. A destination change discards results and reloads the page once (`RELOAD_KEY`) so the new search is captured cleanly.
3. **Resort list.** `loadResorts()` fetches the official eligible-hotels page, extracts hotel codes from links, and caches them in `localStorage` for `CONFIG.cacheDays`.
4. **Scanning.** `scheduleAutoScan()` → `runScan()` iterates eligible hotels; `scanHotel()` → `discoverRooms()` (room types, cheapest first) → per-room rate GraphQL via `post()`/`ask()` → `extractRates()` applies the match rules. Quick mode stops at a hotel's first match; `expandHotel()` does the full scan. `needsRetry()` decides what "Quick scan" retries. Throttling and caps are in `CONFIG` (`delay`, `maxHotels`, `maxRooms`) — keep the script gentle on Hilton.
5. **Points & currencies.** `loadPoints()` re-issues the search asking only for points prices (what Hilton's "Use Points" toggle would do), one request per results page; it runs while Cash vs. Points or Free Night Finder is on (`wantsPoints()`). `rewardType()` reads Standard vs. Premium Room Reward from the hhonors rate plan name; `freeNights()` ranks the hotels for the Free Night Finder. `loadCurrencies()` caches Hilton's converter factors (relative to USD) for 12 h; `convert()`/`valuation()` compute value per point in euro cents against the user's `pointValue`.
6. **Split Stay.** On demand only: `loadSplit()` sends, per night of the stay and per captured results page, one cash (`NIGHT_CASH_QUERY`, USD) and one points (`POINTS_QUERY`) one-night `shopMultiPropAvail` request into `state.split`. `splitStays()` (cached) runs `mixPlans()`, a DP over nights choosing cash nights, certificate nights (Standard only) and reward bookings (`runPoints()`: cheapest of every 5 Standard nights free), per hotel and for one hotel change (best head of one hotel + best tail of another, shown only if it saves `SPLIT.switchSaving`). Limits are in `SPLIT`.
7. **Flexible Dates.** On demand only: `loadCalendar()` sends, per arrival shift of `calendarShifts()` (±`state.calendarRange` days, none in the past) and per captured results page, one cash (`NIGHT_CASH_QUERY`, USD, whole stay) and one points (`POINTS_QUERY`) request into `state.calendar`; the searched dates reuse `state.hotels` (`calendarKinds()`). `calendarTable()` builds the hotel × arrival day matrix per night in cash or points (`state.calendarMode`). The tool key is `calendar` (IDs `hpt-cal-*`, since `hpt-dates` is the header subtitle). Limits are in `CALENDAR`.
8. **Rate Inspector.** On demand only: `inspectRates()` loads the room types (`QUICK`, unless the scan's `state.results` entry has them) and the rates of one room type (`FULL`, plus one per `SPECIALS` entry when `state.inspectSpecial`) into `state.plans` by `planKey()`. `extractRates()` also stores each scanned room's raw rates there, so scanned rooms need no request. `ratePlans()` flattens them (Honors discount as its own plan), `rateKind()` labels them, `inspectPlans()` sorts and computes the markup over the cheapest nightly rate. `ask(…, false)` keeps these requests out of the scan's time estimate. `openInspector()` is the target of the `data-inspect` buttons in Resort Finder and Cash vs. Points.
9. **Suite Finder.** On demand only: `loadSuites()` takes `suiteHotels()` (the picked hotel, else the first `SUITES.maxHotels` of the search) and loads per hotel the room types (`loadRoomTypes()` with `QUICK`, shared with the Rate Inspector; `knownRooms()` reuses what the scan, the Rate Inspector or Suite Finder already has) and their points (`ROOM_POINTS`, `redemptionRoomRates` with `hhonors: true`, read by `roomPoints()`; skipped by `noRewards()` when the search shows no reward rooms) into `state.suites.hotels`. `suiteTable()` compares every room type with the hotel's cheapest one in cash and points; `roomKind()` labels rooms by name (Suite, Villa, Club, View) and `state.suiteShow` filters suites and villas or all upgrades. **Rates** buttons carry `data-inspect-room` for `openInspector(code, room)`. Limits are in `SUITES`.
10. **Price Watch.** The watchlist lives in `localStorage` (`WATCH_KEY`, `loadWatchItems()`/`saveWatch()`, re-read before every write since other tabs share it). `watchRate()` adds a Rate Inspector plan (`planId()`, with the `special` rate it came from) with its search; `checkWatch()` runs `WATCH.startDelay` after `mount()` on every hilton.com page (and on **Check now**), pricing each upcoming stay whose check is older than `WATCH.everyHours` via `priceStay()` (`QUICK` + `FULL` with the stay's own search through the `s` parameter of `variables()`). `rebooks()` feeds the card chip and the minimized badge (`hpt-min-watch`). It does not depend on a search and is not reset by `invalidate()`. Limits are in `WATCH`.
11. **UI.** `mount()` builds one page per key of `VIEWS` (`#hpt-view-home`, `#hpt-view-resort`, `#hpt-view-points`, `#hpt-view-free`, `#hpt-view-split`, `#hpt-view-calendar`, `#hpt-view-rates`, `#hpt-view-suites`, `#hpt-view-watch`); `state.view` picks the visible one, `showView()` switches and persists it, `renderView()` updates the header. A new tool needs a `VIEWS` entry, a `state.tools` and `TOOL_INFO` entry, a page, a card and a switch in the home page's Settings accordion, its summary in `renderHome()`, and a `state.tools` guard on every request it sends. `render()` refreshes everything from `state` (scoped styles, `hpt-` CSS prefix, panel can be dragged/collapsed via `mount()`); `renderProgress()` handles the scan progress/ETA/queue; `exportCSV()` writes `hilton_pro_tools.csv`.
12. **Update check.** `VERSION` comes from `GM_info`. `checkUpdate()` reads the published `@version` (cached in `localStorage` for `UPDATE.everyHours`), `changelogNotes()` turns `changelog.md` into the entries since `VERSION` (bold lead-ins only, so keep that format), `renderUpdate()` draws the home banner, the minimized badge and the version row in Settings; `installUpdate()` opens `@downloadURL` and reloads the tab when the user comes back.

## Conventions

- All persisted keys, the panel ID and CSS classes use the `hilton-pro-tools` / `hpt-` prefix.
- Escape every interpolated value in panel HTML, including attributes, with the `html()` helper; CSV cells starting with `=`, `+`, `-`, `@`, tab or newline get a leading `'`.
- UI text, CSV headers and comments are in English.
- No external servers: all tool requests go to hilton.com with the user's session. The one exception is the update check (section "Update check"), which reads `hilton-pro-tools.meta.js` and `changelog.md` from raw.githubusercontent.com with `credentials: 'omit'`; it can be turned off in Settings. It uses the page's `fetch` (`@grant none`), so Hilton's Content-Security-Policy could block it; the panel then shows *Check failed*.
